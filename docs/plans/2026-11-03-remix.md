# Remix a video — plan

- **Status:** draft 1 (2026-11-03). Not built. Favorites, the other half of the same request, shipped alongside this plan.
- **Ask (owner, 2026-11-03):** from a video, press **Remix**, say what should change, and get a new video. The new video starts from the original's composition, prompts and settings rather than from scratch: "reuse this, but change this, this and this". In effect, a clone plus a revision.
- **Builds on:** revisions (`reviseVideo` in `src/domain/videos.ts`, the `revision` run kind in `src/lib/run-manifest.ts`, `scripts/prepare-run.ts`), media snapshots (`version_media`), and the trust model in the README.

---

## 1. Do we already save what a remix needs? Yes

Every finished version keeps its full composition. Nothing new has to be stored for remixing.

| What                                                                                                  | Where                                                                     | Kept until                     |
| ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------ |
| The whole `video/` dir: `index.html`, `summary.json`, every asset the agent made, AI voice-over clips | `sources` store, `{jobId}/v{n}.tar.gz`, hash in `outputs.sha256`          | the video is deleted           |
| Files kept outside the archive (a recorded narration bus)                                             | `videos` store `{jobId}/v{n}/…`, listed in `{jobId}/v{n}.references.json` | the video is deleted           |
| Library media the run used (logos, screenshots, music)                                                | not in the archive: `version_media` rows hold each item's key and hash    | the media item's own lifecycle |
| Prompt, length, sound, AI voice-over settings, accepted plan                                          | `versions` row                                                            | forever                        |

Edited (render-unchanged) versions write the same `source.tar.gz`, so they can be remixed too.

Revisions already restore a parent's archive into `video/` and tell the agent to change it. A remix is the same run, with two differences:

- The parent version belongs to **another video**.
- The result is a **new video**, owned by the person remixing.

## 2. Gotchas the design has to handle

1. **Every run check assumes one video.**
   - `verifyRunManifest` requires source keys to start with `${jobId}/`, and `prepare-run.ts` rejects a manifest for another job.
   - `readReferences` checks keys against the output's job.
   - The reconciler looks the parent up in the version's own job.
2. **Deleting the original deletes its sources at once.** `deleteVideo` queues `delete_prefix` cleanups for `{jobId}/` in `sources`, `videos` and `bundles`. A remix that points at the original's keys would fail its first run, or a later **Try again**, if the original is deleted meanwhile.
3. **Recorded narration is tied to one video.** Takes have `media.scopeJobId`, and `media_refs` are per job. The narration bus is someone's own voice, and a remix usually retimes scenes, so the old take wouldn't fit anyway.
4. **Plans are tied to one video.** New videos need a plan with `jobId` null; revisions need the job's own plan.
5. **Comments, verdicts, publications and caption revisions** are about the original. A remix shouldn't inherit them.

## 3. Design

### 3.1 Copy the source into the new video (fixes gotchas 1 and 2)

When a remix is created, copy the original version's `source.tar.gz` into the new video's own prefix:

- Copy to `sources/{newJobId}/remix-source.tar.gz`, then verify the hash.
- After the copy, every run-side check stays per-job and unchanged.
- The remix survives the original being deleted.
- Deleting the remix cleans up the copy with everything else under its prefix.
- Composition archives are small (KBs to a few MB with voice clips), so copying them is cheap.

Order of operations:

1. Read and verify the original's archive.
2. Write the copy.
3. In one transaction, insert the job and v1, recording the copy's key and hash.

A copy left behind by a failed transaction is swept by a `delete_prefix` cleanup row, written before the copy.

### 3.2 A new run kind: `remix`

`RunKind` gains `remix`. Its manifest carries `source: { key: '{newJobId}/remix-source.tar.gz', sha256, parentN: null, references: [] }` plus a `remixOf: { jobId, n, title }` block that is informational only.

- `prepare-run.ts` unpacks it exactly like a revision. The `parentN` type widens to `number | null`.
- No reference files are restored: a narration bus is never carried over (gotcha 3).
- The reconciler takes the source from the version's own `remix` column (below), not from `getOutput(jobId, parentN)`.
- Finalize skips caption carry-over, because there is no parent in this job.

### 3.3 Data

Migration `remix`:

- `jobs.remix_of_job_id text`, `jobs.remix_of_n integer`: provenance, for "Remix of …" links and a remix count.
- `versions.remix jsonb`: `{ sourceKey, sourceSha256, fromJobId, fromN }` on a remix's v1, null otherwise.

### 3.4 What the remix copies

| Copied (each one can be overridden in the remix form)              | Not copied                                                           |
| ------------------------------------------------------------------ | -------------------------------------------------------------------- |
| Composition (source archive)                                       | Recorded narration and its takes (the agent is told there is none)   |
| Aspect, language, length (`targetDurationSec`)                     | Comments, verdicts, publications, notifications                      |
| Sound, AI voice-over settings (the voice files are in the archive) | Caption revisions (captions come from the new render)                |
| `version_media` rows (keys and hashes, so the bytes are the same)  | The accepted plan; a remix can make its own plan with the new prompt |
| The prompt history v1…vN, given to the agent as context            | Private flag: see §5                                                 |

If the user changes the aspect, the agent is told to re-lay out for the new frame, which is a larger change. The form says so.

### 3.5 The agent's prompt

A remix prompt is a revision prompt with a different header:

- **Header:** "This is a remix of _{title}_ v{n} by {owner}. `video/` holds its finished composition."
- **History:** the original's prompt history, oldest first, labelled as background.
- **Instructions:** "Make these changes: {remix prompt}. Keep everything else as it is."
- **Title:** the agent picks a new title for the new video. The fallback is "{title} (remix)".

`PROMPT_TEMPLATE_VERSION` goes up by one.

### 3.6 API, MCP, UI

- **API:** `POST /api/v1/videos/{id}/remix`, with an `idempotency-key` header (scope `videos.remix`).
  - Body: `{ fromVersion?, prompt, aspect?, durationSec?, sound?, voiceover?, mediaIds?, planId? }`.
  - Returns 202 with the new video and a `Location` header, then calls `kick`.
  - `fromVersion` defaults to the latest ready version.
  - Video DTO gains `remixOf: { id, n, title } | null`, which is null when the viewer can't see the original.
- **MCP:** a `remix_video` tool that mirrors `revise_video` (`video_id`, `change`, `from_version`, overrides). It is named in the server instructions next to `revise_video`.
- **UI:**
  - **Video page:**
    - A **Remix** button in the header, for Creators, next to Edit, on ready versions. It remixes the version being viewed.
    - It opens a dialog showing the original's prompt (collapsed), a "What should change?" box, and the same Sound, voice-over, length, aspect and media controls as a revision.
    - **Remix** creates the video and goes to its page.
  - **New video's page:** "Remix of _Title_ v3" under the title, linked.
  - **Original's page:** "2 remixes", linked to a Library filter. This is optional and can come after the first release.

## 4. Permissions

- Remixing needs `video:create` (Creators and Admins). It spends credits, billed to the person remixing.
- The original must be visible to them (`canSee`), and its version must be `ready`.
- Remixing someone else's video is allowed, like revising one is today. The original's owner is not notified in v1 (§6, question 3).
- **Trust model:** this doesn't widen it. Runs can already read any blob (README), and the server checks visibility before it copies.

## 5. Private originals

A private video is visible only to its owner and admins, so only they can remix it. The remix starts **private** when the original is. The remixer can change that afterwards, like any of their own videos.

## 6. Questions for the owner

1. Should changing the aspect be allowed in a remix? It is in this plan, with a warning.
2. Should the remix count and links on the original ship in v1, or come later?
3. Should the original's owner get a notification when someone remixes their video?
4. Should a remix with a recorded-narration source keep the recorded voice? This plan drops it (gotcha 3).

## 7. Build order

1. **Data and runs:**
   - The migration.
   - `RunKind` `remix`, with its manifest verification.
   - `prepare-run` accepts `parentN: null`.
   - The reconciler branch, and finalize's skip of caption carry-over.
   - Tests: a remix run on the memory store and on PGlite; and a remix whose original is deleted after it's created still runs.
2. **Domain:**
   - `remixVideo`: the visibility check, the source copy with its cleanup row, the settings copy, the `version_media` copy, idempotency.
   - The remix prompt.
   - Tests for permissions, private originals, not-ready versions and the overrides.
3. **API, MCP and OpenAPI:**
   - The route, `remixOf` on the DTO and the MCP tool.
   - `npm run openapi:gen`.
   - The mock server routes.
4. **UI:** the Remix dialog and the provenance links. Check them in the mock build, in both themes.
5. **End to end:** `scripts/e2e/remix.ts` against production. It remixes a ready video with a one-line change, checks that the new video's first frame still looks like the original, and that the change is there.
