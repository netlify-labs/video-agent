- **Status:** built, deployed and verified on production (2026-11-04: `81f29f2`, `f140741`, `b9476b7`, `975a1ae`; live gate passed with a remix made in the app, §11). As built: §11.
  - Draft 1 went to two independent remote reviews (Fable 5.1 high and Codex gpt-6.1-sol high, both "sound with changes"). Every claim was checked against the code before being folded in (§10).
  - Draft 3 adds the owner interview (§0). Every question is decided; nothing is open.
  - Favorites, the other half of the same request, shipped in `abe1495`.
  - **Beads:** epic `va-p62w` (35 beads: the epic, 5 phase epics, 29 tasks; label `remix`, plus `phase-1`…`phase-5`). Spec keys map to bead ids in `.beads/remix-keymap.json` (1.1 = `va-p62w.1.1`, phase gates `*.G`). Start with `br ready -l remix`; 1.1 and 2.1 can run in parallel.
- **Ask (owner, 2026-11-03):** from a video, press **Remix**, say what should change, and get a new video. The new video starts from the original's composition, prompts and settings rather than from scratch. In effect, a clone plus a revision.
- **Builds on:** revisions (`reviseVideo` in `src/domain/videos.ts`, the `revision` run kind, `scripts/prepare-run.ts`), plans (`src/domain/plans.ts`), media snapshots (`version_media`), the contract's narration layer (`src/lib/contract.ts`), the share page (`netlify/edge-functions/public.ts`), and the trust model in the README.

## 1. Do we already save what a remix needs? Yes

Every finished version keeps its composition. A remix needs no new kind of storage.

| What                                                                                                                       | Where                                                                                                    | Kept until                                                                                               |
| -------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| The composition: `index.html`, `summary.json`, assets the agent made, AI voice-over clips (`assets/voice/`), music credits | `sources` store `{jobId}/v{n}.tar.gz` (≤ 10 MiB tar limit), hash in `outputs.sha256` (`finalize.ts:217`) | the video is deleted                                                                                     |
| What the archive leaves out                                                                                                | dot-paths, `node_modules`, `renders`, top-level MP4s, `feedback/`, library media, the narration bus      | (`bundle-manifest.ts:32-40`)                                                                             |
| A recorded narration bus                                                                                                   | `videos` store `{jobId}/v{n}/narration-bus.wav`, listed in `sources` `{jobId}/v{n}.references.json`      | the video is deleted                                                                                     |
| Library media the run used                                                                                                 | `version_media` rows (media key and hash)                                                                | while referenced: soft-deleting a library item keeps its bytes for versions that use it (`media.ts:373`) |
| Prompt, length, sound, AI voice-over settings, accepted plan                                                               | `versions` row                                                                                           | the video is deleted (soft delete; the rows stay)                                                        |

Edited (render-unchanged) versions write the same kind of `source.tar.gz` from their render, so their finished output can be remixed too.

A revision already restores a parent's archive into `video/` and asks the agent to change it. A remix is that run with three differences:

- The parent version is in **another video**.
- The result is a **new video**, owned by the remixer.
- Some of the parent's state must be **dropped**: recorded narration, edit state and captions.

## 2. Gotchas the design has to handle

1. **Every run check assumes one video.**
   - `verifyRunManifest` requires source keys under `${jobId}/` (`run-manifest.ts:308-310`).
   - `prepare-run.ts:478` rejects another job's manifest.
   - `readReferences` checks keys against the output's job (`bundles.ts:112`).
   - The reconciler finds the parent by `version.parentN` in the version's own job (`reconciler.ts:252-255`).
2. **Deleting the original queues deletion of its files.** `deleteVideo` tombstones the job at once and queues `delete_prefix` cleanups for `{jobId}/` (`videos.ts:640-649`). The next sweep deletes them. A remix that still pointed at the original's keys would fail its first run or a later **Try again** (`retryVersion` makes a new attempt that re-reads the source, `reconciler.ts:431-443`).
3. **A narrated version's composition still contains its narration**, even though the archive leaves out the bus file.
   - `index.html` keeps `<audio id="va-narration">` pointing at `assets/narration/bus.wav`.
   - The AI voice is muted or ducked under it.
   - `summary.json` keeps `narration: true` caption cues (`contract.ts:26-36`).
   - Restoring it without the bus leaves a dangling audio element and stale captions, so it has to be removed deterministically.
4. **Recorded narration is tied to its video.** Takes carry `media.scopeJobId`, and `media_refs` are per job.
5. **Plans are tied to one video.** New videos need a plan with `jobId` null; revisions need the job's own plan with its `baseN` (`videos.ts:112-115`, `plans.ts:281-307`).
6. **Comments, verdicts, publications and caption revisions** are about the original. None of them carry over.
7. **Cleanup rows are unconditional and unique per `(store, prefix)`.**
   - The sweep deletes any due row's prefix, with no notion of "the video exists" (`cleanup.ts:29-32`).
   - `insertCleanup` is `onConflictDoNothing` on `(store, prefix)` (`drizzle.ts:1192`).
   - So a cleanup row for `{newJobId}/` would either delete a remix that succeeded, or later swallow `deleteVideo`'s row.
8. **Music is re-picked for versions without a parent.** `needsMusicPick` skips the Openverse pick only for a revision of a version with sound (`music-pick.ts:44-57`). A remix's v1 has `parentN` null.
9. **The title fallback matters.** Finalize replaces the title with the agent's only while it still equals `deriveTitle(v1.prompt)` (`finalize.ts:483`).
10. **The share page is the same for everyone.** The edge function has no database access and serves one page to every visitor (`public.ts`), so the "who is viewing" check has to happen in the browser.

## 3. Design

### 3.1 Copy, clean and adopt the source into the new video

When a remix is created, `remixVideo`:

1. Refuses when `settings.remixEnabled` is off (`409 remix_disabled`, a new `ErrorCode` like `narration_disabled`, `errors.ts:9`, `:27`). It checks the remixer can see the original (`canSee`) and the version is `ready`, **before** the idempotency lookup, as `reviseVideo` does (`videos.ts:391-392`).
2. Allocates the new job id and writes a **reservation** cleanup row: store `sources`, prefix `{newJobId}/remix-source`, `nextActionAt` = now + 1 hour.
   - The prefix is narrower than `{newJobId}/`, so it never collides with `deleteVideo`'s row (gotcha 7).
3. Reads the original's `source.tar.gz` (buffered `get`/`set`; `BlobsPort` has no copy). Verifies its hash, and refuses sources over the preview extraction limits (`tar.ts:12`) with `400 invalid_request` ("This version is too large or damaged to remix.").
4. **Cleans** a narrated archive (`version.narration` set, or `references.json` in its hashes):
   - Unpacks it in memory.
   - Removes the narration layer with `applyNarration(…, null)` (`contract.ts:789`), which must also restore a muted or ducked AI voice; a test proves it.
   - Drops `narration: true` cues from `summary.json`.
   - Validates the result with the contract checker, then repacks.
5. Writes the copy to `sources/{newJobId}/remix-source.tar.gz` and records its hash.
6. In **one transaction**:
   - Inserts the job, v1 and the attempt, and snapshots `version_media` (the chips left in the dialog).
   - Consumes the plan, if any.
   - Records the idempotency key.
   - **Adopts** the copy by marking the reservation row done. `listDueCleanup` only takes rows with `doneAt` null.
   - A failed transaction, or one that loses a race on the same key, leaves the row open, and the sweep removes the orphan copy within the hour.

From then on everything is under the new video's prefix:

- Run-side checks stay per-job.
- **Try again** never touches the original.
- Deleting the remix removes the copy with everything else.

### 3.2 Runs: reuse the `revision` kind

`prepare-run` and `render-job` are already driven by `manifest.source`. The remix rules live on the server:

- **Reconciler** (`reconciler.ts:252`): add a branch before the `parentN` one. When `version.remix` is set, build the source from it (`key`, `sha256`, no references), never from `getOutput`.
  - The manifest's `source.parentN` is `null`. Widen the type in `run-manifest.ts`, the reconciler's local `revision` type (`:152`) and `buildPrompt`'s input (`prompt.ts:23`).
  - Omit `references` when there are none; an empty array is rejected (`run-manifest.ts:318`).
- **`parentSourceSha256`** on the attempt is the copy's hash.
- **`needsMusicPick`:** returns false when `version.remix` is set and the source's sound isn't `silent` (gotcha 8). `assets/music/credits.json` travels in the archive, and finalize rereads it (`finalize.ts:447`).
- **`prepare-run.ts:488-492`:** the message reads "Restored video/ from the video being remixed" when `parentN` is null.
- **Finalize** needs no change: caption carry-over only runs for frozen narration (`finalize.ts:242`), and editability is recomputed (`finalize.ts:280-282`).

### 3.3 Data

Migration `remix`:

- `jobs.remix_of_job_id text`, `jobs.remix_of_n integer`: the immediate source only (§0, Lineage).
- `versions.remix jsonb` on a remix's v1, null otherwise. It holds everything a run or a retry needs, so nothing is re-read from the original:
  - `sourceKey`, `sourceSha256`: the cleaned copy.
  - `fromJobId`, `fromN`, `fromTitle`, `fromOwnerName`: snapshotted display text.
  - `history`: the source's prompt history up to `fromN`, oldest first. When the source is itself a remix, its v1's own `remix.history` comes first. Capped to the newest 8 entries and 4,000 characters.
  - `fromSummary`: the source output's `agentSummary`, capped at 1,000 characters.
  - `narrationDropped: boolean`.
  - `sourceSound`: the source version's sound, so `needsMusicPick` never reads the original.
- `plans.remix_from_job_id text`, `plans.remix_from_n integer`: a plan made for a remix. Its `jobId` is null (it makes a new video), and `remixVideo` accepts only a plan whose remix source matches the request (gotcha 5).
- `settings.remix_enabled boolean not null default true`.

### 3.4 What the remix carries over

| Copied (each one can be changed in the remix dialog)                                                                                            | Not copied                                                                                |
| ----------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| The finished composition (cleaned of recorded narration)                                                                                        | Recorded narration and its takes; `narration`, `captions` on the version                  |
| Aspect (with a warning when changed), language (transcription only), length (pre-filled from `targetDurationSec`)                               | Edit state: `frozen`, `editedFromN`, `mode` (a remix's v1 is always `author`), `contract` |
| Sound and AI voice-over settings (their files are in the archive)                                                                               | Comments, verdicts, publications, notifications                                           |
| `version_media` as removable chips: inherited snapshots keep working even if the library item was deleted since; newly added items must be live | The accepted `plan` (a remix can plan afresh)                                             |
| Private flag (§5)                                                                                                                               | The original's webhook URL; author and API key (the remixer's)                            |

### 3.5 The agent's prompt

A remix's prompt is a revision prompt with a remix header. It's built only from `versions.remix`, so retries are identical:

- **Header:** "This is a remix of _{fromTitle}_ v{fromN} by {fromOwnerName}. `video/` holds its finished composition."
- **Background:** the snapshotted history and summary, labelled as background and fenced as quoted text.
- **How much to change:** there's no mode toggle (§0), so the agent decides from the request. The prompt says:
  - A remix can be anything from "the same video with a few words swapped" to "a video like this one about something else entirely".
  - Change as much as the request asks. Keep what it doesn't mention: structure, pacing, layout and visual style, unless asked.
  - When the request is a new topic, rewrite the script, on-screen text and AI voice-over lines for it, keeping the source's format.
  - When it's a targeted change, keep everything else exactly as it is.
- **The request:** "{remix prompt}".
- **Brand:** "Apply the current brand from context/ wherever the composition differs from it (colors, fonts, logo)."
- **Media:** the chips left in the dialog are the media for this run. The agent may leave out any that don't fit the request.
- **Narration:** when `narrationDropped` is set, "Its recorded narration was removed; don't add a voice unless asked."
- **Title:** the job's title starts as `deriveTitle(remix prompt)`, as `createVideo` does, and the agent's title replaces it at finalize (gotcha 9).

`PROMPT_TEMPLATE_VERSION` goes up by one.

**Planning:** a remix plan uses the existing planner with `request: "Remix of an existing video: {prompt}"`. Its history is the source's history and summary, the same way a revision plan gets its video's history (`plans.ts:300`).

### 3.6 API and MCP

- **API:** `POST /api/v1/videos/{id}/remix`.
  - Body: `{ fromVersion?, prompt, aspect?, language?, durationSec?, sound?, voiceover?, mediaIds?, planId?, webhookUrl? }`. `webhookUrl` is the remixer's own, as on create and revise; the source's is never copied.
    - `fromVersion` defaults to the latest ready version.
    - `mediaIds` is the final list: it replaces the source's set, and leaving it out keeps the source's set.
  - Takes an `idempotency-key` header, with scope `videos.remix:{sourceId}`.
  - Returns 202 with the new video and a `Location` header, then calls `kick`. Added to `PAID_PATHS` (`app.ts:112`).
- **Plans:** `POST /api/v1/plans` takes `remixOf: { videoId, version }` (mutually exclusive with `videoId`). The plan is checked against the source's visibility.
- **DTO:** `isRemix: boolean` and `remixOf: { id, n, title } | null` on Video.
  - `isRemix` is true for every remix, whether or not the viewer can see the source. It drives the Library's "Remix" mark.
  - `remixOf` is null when the source is deleted or the viewer can't see it.
  - The ETag reflects whether `remixOf` is visible and its title, so a 304 never serves stale provenance.
  - `listVideos` preloads sources separately: `pageRepo.getJob` only finds jobs on the current page (`videos.ts:1084`).
  - Webhook (`'system'`) snapshots leave it out.
- **Config:** `GET /api/v1/config` returns `remixEnabled`; admins set it in Admin → Settings, like `narrationEnabled`.
- **MCP:** a `remix_video` tool mirroring `revise_video` (`video_id`, `change`, `from_version`, overrides). It's removed for roles without `video:create` (`mcp.ts:1484`) and refused when remixing is off. `get_video` and `list_videos` add `remix_of` and `is_remix`.

### 3.7 UI

All entry points open the same **Remix dialog**, and only for people who can create, when `remixEnabled` is on.

- **Remix dialog:**
  - **Header:** "Remix _{title}_ v{n}". The source's prompt history and summary sit collapsed under "What this video was made from".
  - **Prompt box:** empty, labelled "What would you change?", helper "Be as descriptive as possible: a new topic, swapped names, a different length…".
  - **Settings:** the controls revisions use, pre-filled from the source: Sound, AI voice-over, length (the source's), aspect (a warning when changed: "the agent will re-lay out every scene"), language (transcription), and the media chips (removable, plus Add).
  - **Narration note:** for a narrated source, "Your recorded narration isn't carried over."
  - **Plan first:** a checkbox, as on revisions. When ticked, the plan panel opens with the remix's request, and the brief's **Make it** creates the remix.
  - **Remix:** creates the video and goes to its page.
- **Video page:**
  - A **Remix** button in the header next to Edit, on ready versions. It remixes the version being viewed.
  - A remix shows "Remix of _Title_ v3" under its title, linked to the source when the viewer can see it.
- **Library tile menu:** a small "⋯" menu on each tile, beside the favorite star and outside the link, as the star is. Its only item in v1 is **Remix**, which remixes the latest ready version. A remix's tile adds "Remix" to its meta line (owner · time · aspect · Remix).
- **New video page:** a "Start from an existing video" link above the prompt.
  - It opens a search picker over the Library (the same list query, with Mine and Favorites as quick filters) and a version select (latest ready by default).
  - Picking one turns the page into the Remix dialog's form in place. "Start from scratch" goes back.
- **Public share page** (`/v/{slug}`):
  - A small script, the page's only one, asks the app `GET /api/v1/me` (same origin, cookies). It shows a **Remix in Video Agent** link only when the answer says the viewer can create and remixing is on. The link goes to `/videos/{id}?remix={n}`, which opens the dialog.
  - To keep public traffic from calling the API, the app sets a non-secret hint cookie `va_creator=1` (not used for auth) when a Creator or Admin loads it. The script calls `/me` only when that cookie is present.
  - Outsiders see an unchanged page and trigger no API call.
- **Mock server and OpenAPI:** the remix and plan routes, `remixOf`, and `remixEnabled` in `ui/src/mock`; `npm run openapi:gen`.

## 4. Permissions, credits and the kill switch

- Remixing needs `video:create` (Creators and Admins), `remixEnabled` on, and a source that is visible (`canSee`) and `ready`.
- There's no owner opt-out (§0). Remixing someone else's video is allowed, as revising is.
- Credits come from the team, as for every run. Usage is attributed to the remixer through v1's `authorId` and `apiKeyId`.
- **Kill switch:** with `remixEnabled` off, every entry point hides, and the API, plans and MCP refuse. Remixes already queued still run.
- **Trust model:** unchanged. Runs can already read any blob (README), and the server checks visibility before copying.

## 5. Private originals

A private video is visible only to its owner and admins, so only they can remix it.

- The remix starts **private** when the source is, with its access mirror set like `updateVideo` sets one (`videos.ts:605-613`, `files.ts:88`).
- **Known policy, stated plainly:** an admin who remixes someone's private video gets a copy of its content and prompt history, and can later make it public. Hiding the "Remix of" link can't hide copied content; that's the same trust model as admins seeing private videos today. The owner isn't notified in v1.

## 8. Not in v1

- A remix count and reverse links on the original.
- A "Remixes" Library filter.
- A stored lineage chain or root original (immediate source only).
- Notifying the original's owner.
- An owner opt-out from remixing.
- Keeping recorded narration in a remix.
- Translating a video by changing its language: translation is asked for in the prompt.
- Picking the source's comments into a remix.
- Remixing several versions or videos into one.
- Streaming blob copies (the 10 MiB tar limit keeps buffering cheap).

## 9. Follow-up raised in the interview (separate work)

**Dismissible comments in Incorporate feedback.** Today the Incorporate feedback dialog lets you untick comments for one revision (`ui/src/components/Review.tsx:269-360`). Unticked comments stay open and come back the next time, and resolving is a separate owner action. The owner wants to be able to **dismiss** feedback they've decided not to act on: kept for the record, but out of the open list and future Incorporate feedback dialogs. It's tracked as its own task, not part of remix.

**Deviations from §3:**

- **Version media endpoint.** `GET /api/v1/videos/{id}/versions/{n}/media` lists a version's library items (deleted
  ones included) for the dialog's chips. The Video DTO doesn't carry media, and adding it would cost a query per Library
  card.
- **Plan scoping.** `consumePlan` keeps remix plans for `remixVideo` only, and `remixVideo` accepts only a plan for the
  same source and version. Before this, a remix plan (`jobId` null) would have been accepted by `createVideo`.
- **The cleaner also drops a held last frame** (`va-hold`, `assets/hold/*`): it exists only to cover recorded narration
  running past the end. `applyNarration(…, null)` already restored the AI voice's levels, so `contract.ts` is unchanged.
- **A remix's v1 sets `mode: 'author'` explicitly**, rather than relying on the database default (the memory store has
  none).
- **Admin settings** return `remixEnabled` alongside the voice-over settings (`AdminSettings` in
  `narration-settings.ts`).
- **Share page.** The link's script also does nothing inside an embed iframe (the page is the `twitter:player`). The
  link carries the video id, which the share page didn't expose before. A video id alone gives no access.
- **`listVideos` preload.** Sources are loaded one query per distinct source on the page, not one query in total.
