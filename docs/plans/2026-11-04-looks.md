## 0. What a look is, in one paragraph

A **look** is a folder in the repo, `looks/<id>/`, that tells the agent how a video should move and be laid out:
type scale, layout grid, pacing, transitions, textures, how to use the brand's colours, and which ready-made
HyperFrames items suit it. It ships with a short preview clip for the picker and an example composition that passes
the editing contract. A person picks a look on **New video** (or in the API, MCP, SDK and CLI). The run gets that
look's files and follows them; the brand still decides colours, logo, fonts and wording. Every version records which
look it used and keeps a copy of it, so retries and revisions get exactly the same look even after the look changes
in the repo. **Restyle** makes a new version of a video in another look. Adding a look is one folder and one command
to check it, so it's the easiest first pull request in the project.

Why it matters for the open-source launch:

- It's the most visible upgrade there is: the README and the picker can show eight very different videos made from
  the same prompt.
- Today every video comes out in roughly one house style (whatever the agent does with `context/BRAND.md`). Teams
  ask for "more like a magazine", "more like a terminal", "punchier for social" in every prompt, and get it
  inconsistently.
- It absorbs the deferred bead `va-css.3` ("Later: Named templates in video/templates/"), which never got a design.
- Contributions need no backend knowledge: write rules, build an example, render a preview, open a PR.

People-facing words (shared terminology rule): **Look**, **Restyle**, and "scene" for a beat. In code and the API:
`look`, `beat`.

## 1. Facts this plan relies on (checked 2026-11-04)

**The run and its inputs**

- The run prompt is one template with a version number, `PROMPT_TEMPLATE_VERSION` (`src/domain/prompt.ts:8`). The
  number is **not** in the prompt text; it's recorded on each attempt (`src/domain/reconciler.ts:457`).
  `test/remix-run.test.ts:176` pins the literal `16`. Shared rule: each PR that changes the template adds 1, in merge
  order, and the first PR to touch that test makes it import the constant. Looks' phase 2 is first in the merge order.
- The prompt already tells the agent to read the brand: "Read context/ first … If context/brand/ exists, it is this
  deployment's brand kit … it overrides the rest of context/. Follow the brand unless the request explicitly asks for
  something different." (`src/domain/prompt.ts:137`). So the precedence **request > brand** already exists.
- Untrusted text goes into fenced blocks (`<<<` … `>>>`, `src/domain/prompt.ts:66-67`) after `sanitizeBrief`
  (`:106`). Optional features keep the prompt byte-identical when they're off: "silent when missing (the prompt is
  then exactly as before sound existed)" (`src/domain/prompt.ts:38-41`). Looks follow the same rule.
- A revision of a narrated version is locked to the narration's length: "Keep it exactly <length>: the recorded
  narration is that long" (`src/domain/prompt.ts:116`), the locked-narration lines (`lockedNarrationLines`,
  `src/domain/prompt.ts:485`), and `checkNarrationModified` fails when the beats don't add up to the lock
  (`src/lib/narration-modified.ts:155`, the length check at `:306-309`).
- Inputs a run restores come from a **server-written run manifest** whose sha256 is in the prompt
  (`src/domain/reconciler.ts:187-200`, `src/lib/run-manifest.ts:30-64`). There are three `putManifest` calls:
  render-unchanged (`:208`), author-from-frozen, the fit-to-narration run (`:232`), and author/revision (`:317`). The
  last is written only when there is something to restore: `if (revision || media)` (`:316`).
- Before starting a remix run, the reconciler checks its copied source still exists and fails with
  `SourceUnavailable` otherwise (`src/domain/reconciler.ts:258-260`). A look snapshot gets the same pre-flight.
- Comment pins are anchored by time and position (`timeSec`, `x`, `y`; `src/domain/comments.ts:25-27`, `:101-108`,
  and the feedback snapshot at `src/domain/reconciler.ts:303-313`), not by beat id.
- The golden prompt test compares `buildPrompt` byte for byte with `test/fixtures/prompt-silent.txt`
  (`src/domain/prompt.test.ts:76-79`). It's the proof that the prompt doesn't change when a feature is off.
- `verifyRunManifest` accepts only `v: 1`, checks the fields it knows and ignores unknown ones
  (`src/lib/run-manifest.ts:295-320`). So a new optional `look` field needs no version bump, only its own shape check.
  It refuses any key outside the video's own prefix: "Every key stays inside this video's own prefix"
  (`src/lib/run-manifest.ts:308-309`). So a look snapshot must live under `<jobId>/…` in the sources store.
- `prepare-run` puts reference reading outside `video/` so it's never archived: PDFs go to `context/media/`
  (`scripts/prepare-run.ts:433-438`). A look can go to `context/look/` the same way. `restoreArchive`
  (`scripts/prepare-run.ts:104-116`) is the pattern for checking an archive's entries before unpacking.
- A run's deploy is resolved **at run start**: `a.deployId ?? (await deps.platform.productionDeployId())`
  (`src/domain/reconciler.ts:434`). So the checkout a run gets can be newer than the deploy that served the person's
  request.
- The brand kit reaches runs two ways: committed `context/`, or `BRAND_ZIP_URL`, which netlify-agent-kit unpacks into
  `context/brand/` at run start (`package.json:94-107`; `node_modules/netlify-agent-kit/README.md` "Files").

**The build and the function bundle**

- `scripts/build.ts` already turns repo folders into generated modules: `src/generated/context.ts` and
  `src/generated/planning-context.ts` from `context/` or the brand zip (`scripts/build.ts:53-119`). It fetches
  `BRAND_ZIP_URL` itself and falls back to `context/` on any failure, so a bad URL never breaks a deploy
  (`scripts/build.ts:33-53`).
- `writeTarGz` (`src/lib/tar.ts:124`) writes deterministic archives (sorted entries, fixed mtimes) and is already used
  for remix copies (`src/lib/remix-source.ts:118`), but it names every entry `video/${path}` (`src/lib/tar.ts:127`),
  and `restoreArchive` refuses anything outside `video/`. A look archive needs a `prefix` option on `writeTarGz` and
  its own restore helper.
- `src/lib/bundle-manifest.ts` has two parts: `bundleManifest(dir)` walks a composition with `excluded()` (dot paths,
  `feedback/`, top-level `.mp4`, `assets/media/med_*`; `:32-41`), and `manifestHash(files, media)` (`:63`) hashes a
  sorted file list. A look's hash uses `manifestHash(files, [])` over its own file list, not the composition walker.
- The `cleanups` table has a unique index on `(store, prefix)` (`db/schema.ts:691`). Remix never hits it because
  every remix reserves a fresh `${newJobId}/remix-source` (`src/domain/remix.ts:104-111`). `updateCleanup(id, patch)`
  takes a partial row (`src/store/types.ts:332`), so a reservation can be re-opened by id.
- `/assets/*` is served `Cache-Control: public, max-age=31536000, immutable` (`netlify.toml`). Previews with a hash in
  their name can live there.
- Functions don't bundle arbitrary repo files today: `netlify/functions/api.ts` imports generated modules only, and
  nothing in `src/` reads files from disk at run time. Netlify's `[functions] included_files` (globs relative to the
  project root) adds files to the function bundle (Sources). How a function finds them at run time, and whether the
  globs match dot-directories, are checked in spike K3 rather than assumed.
- The Netlify build has no browser. CI does: it installs Playwright's Chromium before the UI tests
  (`.github/workflows/ci.yml:24`).

**Data**

- `versions` holds per-version choices as columns and jsonb: `sound`, `voiceover`, `narration`, `captions`, `remix`,
  `plan` (`db/schema.ts:91-126`). A `look` jsonb column fits next to them.
- Admin switches are columns on the single `settings` row: `narration_enabled`, `remix_enabled`
  (`db/schema.ts:19-35`), read through `src/domain/narration-settings.ts` and exposed as
  `GET/PATCH /api/v1/admin/settings` (`src/app.ts:966-981`, schemas `src/schemas.ts:1404-1436`).
- Create, revise and remix inputs: `CreateVideoInput` (`src/domain/videos.ts:56-66`), `ReviseInput`
  (`src/domain/videos.ts:68-82`), `RemixInput` (`src/domain/remix.ts:35-49`). Sound is the model to copy: optional,
  resolved once and stored on the version (`versionAudio`, `src/domain/videos.ts:364`), and a revision with sound
  omitted keeps "the parent's sound" (`src/domain/videos.ts:78`), never a default.
- `createVideo` mints the video id inside its transaction (`src/domain/videos.ts:318-321`). Remix mints the new id
  first, copies the source **outside** the transaction (blob writes can't roll back), writes it, reads it back and
  compares the sha256 (`src/domain/remix.ts:127-130`), and only then opens the transaction (`:181`). A reservation
  cleanup row is committed before the copy and marked done when the remix is adopted, so the sweep deletes a copy
  that was never adopted (`src/domain/remix.ts:6`, `:55-59`, `:105`, `:173`, `:257-258`, `:270-271`).
- Deleting a video queues a `delete_prefix` cleanup of its stores (`src/domain/videos.ts:659-682`), so anything stored
  under `<jobId>/` is cleaned up with it.
- Webhook payloads embed the version DTO: `video: await videoDto(repo, deps, e.jobId, 'system')`
  (`src/domain/webhooks.ts:56-57`). A `look` field on the DTO reaches webhooks with no extra code.

**Plans**

- The planner's router returns a template (`launch`, `tutorial`, `social`, `changelog`, `sales`, `other`) and a model
  (`src/domain/plans.ts:1-5`, `:44-51`; the route object at `:358-364`). The brief step "decides" sound when the
  person didn't (`decideSound`, `src/domain/plans.ts:576-590`) and passes choices as labelled data blocks
  (`chosen_shape`, `chosen_sound`, `src/domain/plans.ts:517-520`).

**The editing contract**

- Colours are any `--va-color-<role>` on `#root`; the validator reads every role and requires at least one
  (`src/lib/contract.ts:248-253`, `:552`). The editor edits roles by name (`src/lib/contract.ts:1148`). So a look can
  add roles (`glow`, `grid`) without a contract change.
- The editor's colour button prints the role's raw value (`ui/src/pages/Edit.tsx:1357-1359`). A `color-mix(…)`
  expression would show as that whole string and couldn't be edited with the colour picker. **Looks write derived
  roles as literal colours** the agent computes from the brand.
- Beats must be direct children of the root, each with its own `vaBeat` script that selects only inside its element
  and never touches `document` or `window.__timelines` (`src/lib/contract.ts:395-445`). Any other timed root child
  that isn't a layer fails (`:449-455`). The validator never mentions `data-composition-src`, so whether a mounted
  sub-composition **inside** a beat passes, and whether the editor copes, is unverified: spike K1 settles it.
- HyperFrames registry **blocks** install as separate sub-composition files with their own timeline, mounted with
  `data-composition-src`; **components** are snippets merged into a scene (hyperframes-registry skill, "Wiring").
  Text inside a block's own file isn't in `video/index.html`, so the editor can't edit it. **Looks prefer components
  and inline any block they use.**

**The registry**

- `video/hyperframes.json` points the registry at `https://raw.githubusercontent.com/heygen-com/hyperframes/main/registry`:
  the `main` branch, while the CLI is pinned at 0.8.222 (`netlifyAgent.hyperframes.version`, `package.json:96`; the
  `hyperframes` dependency, `package.json:71`; `video/package.json:6-9`). So "use
  `grain-overlay`" can resolve to different source on different days. Upstream has a `v0.8.222` tag (checked with
  the GitHub API, 2026-11-04). `hyperframes add` "needs the network even for an item installed before"
  (hyperframes-registry skill).
- The registry index at that tag (`registry/registry.json`) types each item. Of those named in §5, these are
  **blocks** (`hyperframes:block`): `code-diff`, `bar-chart-race`, `data-chart`, `beat-freeze-cut`, `camcorder-hud`,
  `editorial-flash-overlay`, `canopy-part-title`, `code-slice-hero`, `chromatic-radial-split`, `lt-clean-bar`. These
  are **components** (`hyperframes:component`): `blur-in`, `grain-overlay`, `bottom-up-letters`,
  `browser-device-stage`, `agent-cursor`, `before-after-wipe`.
- The HyperFrames repo is Apache-2.0 at that tag; the registry index has no per-item licence field, so each item's
  licence has to be read from its own files upstream (spike K4).

**A naming collision to handle**

- `RENDER_QUALITY` already has a value called `looks` (README configuration table: `looks`, `standard`, `delivery`;
  `scripts/render-job.ts:50`). Env vars for this feature are `LOOKS_*`, and docs say "render quality" for the other
  one (§14 Q1).

## 2. Gotchas the design has to handle

1. **Looks change after a version is made.** Someone improves `kinetic` next month. A retry of an old attempt, or a
   revision of an old version, must not silently pick up different rules. → Snapshot the look per version (§4.3).
2. **The run's checkout isn't the deploy the person saw.** The deploy is resolved at run start
   (`reconciler.ts:434`), and a deploy can land between "Create" and the start. → The snapshot is taken when the
   version is created, from the archive in the function bundle of the deploy that served the request.
3. **Manifest keys must stay inside the video's prefix** (`src/lib/run-manifest.ts:308`). → Store the snapshot at
   `<jobId>/looks/<hash>.tar.gz`, copied once per video, cleaned up with the video.
4. **Blob writes aren't transactional, and the reservation's prefix repeats.** Unlike a remix, a revision reuses the
   video's id, so the same `<jobId>/looks/<hash>.tar.gz` can be reserved twice, and `cleanups` has a unique
   `(store, prefix)` index (`db/schema.ts:691`). An unadopted copy also *looks* present until the sweep deletes it.
   → A deterministic reservation id, re-opened rather than re-inserted; a copy is skipped only when a committed
   version already references the key, never because the blob exists (§4.3).
5. **A version whose snapshot is gone would burn credits on every retry**, failing inside the runner after the run has
   started. → The reconciler checks the snapshot exists before it starts an attempt, as it does for remix copies
   (`src/domain/reconciler.ts:258-260`), and fails the attempt with a clear message (§4.6).
6. **Registry blocks break editability** if mounted as sub-compositions. → Looks prefer components, inline any block
   into a beat (markup, scoped CSS, its timeline rewritten in the beat's `vaBeat`), and spike K1 proves it for every
   block the starter set uses.
7. **Registry `main` moves.** → Pin the registry URL to the CLI's tag for every run (§4.5), and vendor what looks use.
8. **Brand vs look disagreements.** A "Retro CRT" look wants green phosphor; the brand is orange. → Fixed precedence
   (§3) and a colour rule: a look uses the brand's roles and may only derive new ones from them, as literals.
9. **Token cost.** The example composition, not `LOOK.md`, is the big read. → `LOOK.md` ≤ 12 KB is required reading;
   `example/index.html` ≤ 24 KB is reference only ("skim the beat that matches the one you're writing").
10. **The agent copies the example.** → The example uses an obviously fictional product and placeholder words, and
    the prompt says never to reuse its words, only its structure.
11. **Imitation.** Contributors may want "the Apple keynote look" or a specific film's titles. → Looks are original or
    generic genres; the contribution guide says so and review enforces it (§8).
12. **The prompt must not change when no look is used**, so existing tests, retries and costs stay the same. → No look
    means no look lines: the prompt text is byte-identical to today's, proven by the golden fixture
    (`test/fixtures/prompt-silent.txt`), which phase 2 does not regenerate. **And the default is no look** until spike K2
    shows `clean` costs about the same as no look (§6), so API, MCP and Action callers don't get a silent change.
13. **Restyle and recorded narration.** A narrated revision must keep its exact length and beat sum. → v1 refuses a
    restyle (and a look change on remix) of a version with recorded narration (`409 look_not_allowed`, §4.3).
14. **Name collision with `RENDER_QUALITY=looks`** (§1). → Naming rules.
15. **Untrusted text from looks.** A look's name and description reach the brief prompt, `list_looks` and the UI, and
    once team looks exist (§12) they come from a zip rather than reviewed PRs. → Length caps in the schema,
    `sanitizeBrief` / the planner's data blocks wherever they enter a prompt, text-only rendering. A look's name and
    description are visible to every signed-in role (even when disabled), so they're no place for anything private.
16. **Contributed example HTML and JS run in CI's Chrome.** → `look:check` runs only on the `pull_request` trigger
    (no secrets, read-only token), never `pull_request_target`; the contribution guide says so.

## 3. Who decides what: the precedence rule

From strongest to weakest:

| Order | Source | Decides |
| --- | --- | --- |
| 1 | The request (and comments being incorporated) | Anything it explicitly asks for |
| 2 | The brand (`context/`, `context/brand/`) | Colours, logo and its use, fonts, wording, tone of voice, claims |
| 3 | The plan's brief (when there is one) | Story, beats, length, message, call to action |
| 4 | The look (`context/look/`) | Layout and grid, type scale and weights, pacing, motion and easing, transitions, textures, how colour roles are used, caption style, sound mood |
| 5 | The defaults in `video/AGENTS.md` and the HyperFrames skill | Everything else |

Rules that make this concrete:

- **Colours.** A look never brings hex values for the brand's roles (`bg`, `text`, `muted`, `accent`, …). It says
  how to use them ("one accent per frame; large flat fields of bg; text never on accent"). It may add roles derived
  from the brand's, and the agent writes each as a **literal colour** it computes from the brand's hex
  (`--va-color-glow: #ffb38a`, "the accent mixed 40 % toward white"), never as `color-mix(…)`, so the editor's colour
  picker works on it (§1). Retro CRT uses the brand accent as its phosphor colour. A person who wants green phosphor
  asks for it, and the request wins.
- **Fonts.** The brand's fonts win for every role the brand defines. In v1 a look ships no fonts: for a role the
  brand lacks it names a CSS font stack (Terminal: `"JetBrains Mono", ui-monospace, Menlo, monospace`; K1 found the stack must lead with a family the renderer has).
  Fonts shipped inside looks (an OFL or Apache WOFF2 used only when the brand has none for that role, such as a marker
  hand for Whiteboard) come with phase 4 (§12 has the design).
- **Type scale.** The look owns sizes and ratios ("headline 9 % of frame height, never more than 5 words a line"),
  but the brand's hard rules ("headlines are 96 px") win when the brand states them.
- **Sound.** The look suggests a music mood (`"synthwave, 100 bpm"`) used when Sound is on and nothing was picked. It
  never turns sound on by itself.

## 4. Design

### 4.1 The folder

```
looks/
  README.md                  what a look is, the quality bar, how to add one (§8)
  PROMPTS.md                 three standard prompts every look is shown with in its PR
  _template/                 what `npm run look:new` copies
  clean/
    look.json                metadata (§4.2), validated with zod
    LOOK.md                  the rules the agent follows (§4.4), ≤ 12 KB
    preview.mp4              ≤ 6 s loop, muted, H.264, 540 px on the long side, ≤ 500 KB (the picker's hover clip)
    poster.webp              ≤ 60 KB (the picker's card)
    example/                 a complete composition that passes contract v1 and `hyperframes check`
      index.html             ≤ 24 KB
      summary.json
      assets/…               placeholder media only
    registry/                vendored HyperFrames items this look uses (§4.5)
      grain-overlay/…
      registry.lock.json     item → upstream path, tag, sha256 of each file, licence
    assets/                  textures and CC0 sound effects, ≤ 1 MB (fonts come in phase 4)
      credits.json           every asset's licence and credit
```

Limits, enforced by `look:check`: the files a run gets (everything except `preview.*` and `poster.*`) total at most
3 MB, no single file over 1 MB, and `assets/` (the only folder the agent may copy into `video/`) at most 1 MB, because
whatever it copies lives in that video's `source.tar.gz`, every revision, every remix copy and every checkpoint. Only
these file types: `.md`, `.json`, `.html`, `.css`, `.js`, `.svg`, `.png`, `.webp`, `.jpg`, `.wav`, `.mp3`, `.ogg`
(`.woff2` returns with fonts in phase 4), and binary files must sniff as what their extension says. No symlinks, no
dotfiles, no paths with `..`.

Why a folder in the repo rather than a database row: looks are authored, reviewed and versioned like code; a PR shows
exactly what changed; the build can validate and catalogue them; forks get them for free. In-app looks come later
(§12).

### 4.2 `look.json`

Validated by one zod schema in `src/lib/looks.ts`, shared by the build, `look:check` and the server. Unknown keys are
refused, so every key another plan needs is declared here.

```jsonc
{
  "id": "kinetic",                        // = folder name; /^[a-z0-9][a-z0-9-]{0,39}$/
  "name": "Kinetic type",                 // ≤ 40 chars, shown on the card
  "description": "Big words that move with the beat. Type is the picture.",   // ≤ 160 chars
  "tags": ["type", "social", "energetic"], // ≤ 8, each ≤ 20 chars, lowercase; the picker's filter
  "bestFor": ["social", "launch"],         // plan templates (src/domain/plans.ts CHECKLISTS keys)
  "aspects": ["16:9", "9:16", "1:1", "4:5"], // shapes the rules cover; built-ins must list all four
  "engines": ["hyperframes"],              // first is preferred; the engine choice rule (§4.14) reads this
  "colors": { "roles": ["bg", "text", "accent"], "derived": ["glow"] },  // roles the example uses
  "sound": { "musicMood": "punchy electronic, 120 bpm" },  // ≤ 120 chars; read by the music pick
  "recording": {                           // optional; used by screen recordings (screen-recording-demo plan)
    "frame": "wallpaper",                  // "wallpaper" | "browser" | "device" | "none"
    "padding": 0.06, "radius": 14, "shadow": "lg",
    "wallpaper": "gradient",
    "cursor": { "shape": "arrow", "scale": 1.3, "color": "text" },
    "ripple": "ring",
    "callout": "pill",
    "zoomMax": 2.2
  },                                       // or "recording": false: this look doesn't suit demos
  "registry": ["bottom-up-letters", "beat-freeze-cut"],  // components first; must match registry/registry.lock.json
  "authors": ["Video Agent maintainers"],
  "license": "MIT",                        // the look's own files; assets keep theirs (credits.json)
  "since": "2026-11-04"
}
```

- `recording` is owned by this plan's schema and used by the screen-recording-demo plan. Its fields are the ones that
  plan's §7 defines; colours come from the brand's roles. A look without the block gets that plan's default
  (`wallpaper` with brand colours). The demo picker hides a look when it says `"recording": false` **or** when its
  `engines` don't include `hyperframes` (screen recordings are HyperFrames-only in v1); this needs this plan's phase 3
  picker. `clean` gets a `recording` block in phase 2.
- `tags` are kept in the schema for later filtering and search, though the v1 picker shows them only as text.
- Why these fields and not more: every field is used by something (the picker, the plan, the music pick, the
  validator, the engine choice, screen recordings). Rules about motion, layout and sound effects belong in `LOOK.md`,
  in words the agent reads, not in JSON the agent would have to interpret. (`pace`, `fonts` and `sound.sfx` were
  dropped in draft 3: nothing read them in v1. `fonts` returns with phase 4, §12.)

### 4.3 Versions record a snapshot of their look

**Column:** `versions.look jsonb` (nullable), shape `VersionLook` in `src/domain/types.ts`:

```ts
interface VersionLook {
  id: string            // 'kinetic'
  name: string          // 'Kinetic type' (kept so the UI can name a look that's since been removed)
  hash: string          // canonical file-manifest hash of the look's run files (src/lib/bundle-manifest.ts)
  key: string           // '<jobId>/looks/<hash>.tar.gz' in the sources store
  sha256: string        // sha256 of that archive
  bytes: number
  source: 'builtin' | 'team'
}
```

**Archives are built once, at build time.** The build (`scripts/lib/looks.ts`) packs each look's run files into
`looks-build/<id>.tar.gz` (a plain directory, gitignored; glob matchers often skip dot-directories, so it isn't
`.looks-build/`). It uses `writeTarGz` with a new `prefix` option: today the helper hard-codes `video/`
(`src/lib/tar.ts:127`), so phase 1.2 adds `writeTarGz(files, { prefix: 'look/' })` with `video/` as the default, which
leaves remix unchanged. The look's `hash` is `manifestHash(files, [])` (`src/lib/bundle-manifest.ts:63`) over the
look's own sorted file list (not `bundleManifest(dir)`, whose `excluded()` rules are for compositions). The build
records `{ hash, sha256, bytes }` for each look in `src/generated/looks.ts`.

`netlify.toml` gets `[functions."api"] included_files = ["looks-build/*.tar.gz"]` (K3: only the API function needs them), so the API function carries exactly the
archives the catalog describes. The function reads them from `join(process.cwd(), 'looks-build', '<id>.tar.gz')`.
Spike K3 confirms that path on a branch deploy and under `netlify dev`; if it fails, the fallback K3 records is
deploy-scoped Blobs written by the build.

**The snapshot copy** happens when a version is created with a look, following remix's copy-then-adopt pattern
(`src/domain/remix.ts`, §1), adjusted because a revision reuses the video's id:

1. Resolve the look (the rule below). **A copy is skipped only when a committed version of this video already
   references the same `key`** (checked again inside the transaction in step 3). The blob merely existing is never
   the signal: an unadopted copy from a failed or concurrent attempt looks present, and the sweep deletes it.
2. Otherwise **insert or re-open** the reservation cleanup row. Its id is deterministic, `look-<jobId>-<hash>`, and
   its prefix is `<jobId>/looks/<hash>.tar.gz`. Because `cleanups` has a unique `(store, prefix)` index
   (`db/schema.ts:691`), a retry after a failed attempt re-opens the existing row with `updateCleanup` (`doneAt: null`,
   `nextActionAt: now + 1 h`) instead of inserting a second one. Then, outside the transaction, read
   `looks-build/<id>.tar.gz` from the function bundle, check its sha256 against the catalog (a mismatch is a server
   error: the bundle is corrupt, never a silent fallback), write it to the sources store (overwriting an unadopted
   copy is harmless: same hash, same bytes), read it back and compare the sha256.
3. The transaction that inserts the version stores `VersionLook` and marks the reservation done. If another committed
   version of this video already references the key by then, the row is marked done too (both versions share the
   blob). A failed insert or an idempotent replay leaves the reservation open; the sweep deletes the copy, and the
   next attempt re-opens the row and copies again.

`createVideo` mints the video id inside its transaction today (`src/domain/videos.ts:318-321`); with a look it mints
the id first, as `remixVideo` does, so the copy can be made before the transaction.

**Resolution.** Explicit `null` always means "no look" and is never turned into the default. The default applies
**only where there's nothing to inherit** (a create, and plans). Written once in `src/domain/looks.ts` as
`resolveLook(input, { inherited?, planLook?, default })` and used by create, revise, remix and plans:

- `input.look === null` → none.
- `input.look` given → that look's current catalog version.
- omitted, with a parent or source version (revise, remix, render-unchanged, fit, redo a scene) → **the parent's
  value, including none**. The default is never consulted, just as a revision keeps the parent's sound
  (`src/domain/videos.ts:78`).
- omitted, create → the plan's look if the plan has one, else the admin default, else none.

A **restyle** is any revision or remix whose resolved snapshot `hash` differs from the parent's: a new id, the same id
at a newer catalog hash, or a look where the parent had none. Passing the parent's own id at the same hash isn't a
restyle: no new copy, no restyle lines.

| Action | `look: "<id>"` | `look` omitted | `look: null` |
| --- | --- | --- | --- |
| Create | that look's current version | the plan's look, else the admin's default look (none until §6 changes it), else none | no look |
| Revise | that look's current version (a **restyle** unless it's the parent's own hash) | the parent's snapshot, unchanged; **none if the parent had none**, even with an admin default set | no look (the agent keeps whatever the composition has) |
| Revise of a version with recorded narration | a restyle is `409 look_not_allowed` ("Restyle isn't available for videos with recorded narration yet"); the parent's own look at the same hash is accepted (not a restyle) | the parent's snapshot | no look |
| Fit to my narration (`author_from_frozen`) | not accepted (`400 look_not_allowed`) | the parent's snapshot; the fit prompt gets the look lines (not the restyle lines) | not accepted |
| Remix | that look's current version (restyle as a new video); refused with `409 look_not_allowed` when the source has recorded narration *and* the remix keeps it (today remix drops recorded narration, so in practice it's allowed) | the source version's look (none if it had none), re-snapshotted under the remix's prefix | no look |
| Edit → Render (render-unchanged) | not accepted (`400 look_not_allowed`) | copied from the edited version (display only; the run doesn't read it) | not accepted |
| Redo a scene (regenerate-beat, `scope` present) | not accepted (`400 look_not_allowed`, raised by `reviseVideo`) | the parent's snapshot | not accepted |

A revision keeps the parent's **snapshot**, not "the current version of the same look id", because the composition
was made with those rules. Someone who wants the improved look restyles into it again.

Why snapshot instead of trusting the checkout: retries must be exact (the remix spec makes the same promise for its
source copy, `src/domain/types.ts:295-298`), revisions must be consistent, and the checkout can be a newer deploy
(§2.2). The cost is up to 3 MB per video in Blobs (usually a few hundred KB), cleaned up with the video.

### 4.4 `LOOK.md`

Plain rules, in the voice of `context/README.md` ("The agent follows rules better than adjectives"). Required
sections, checked by `look:check` (heading text only):

1. **In one line** — what it feels like.
2. **Layout** — grid, margins, safe areas, per shape (16:9, 9:16, 1:1, 4:5), where text sits, how media is framed.
3. **Type** — scale as fractions of frame height, weights, case, tracking, line length, how many words on screen.
4. **Colour use** — how the brand's roles are used; any derived roles and how to compute their literal values.
5. **Motion** — easing curves (named GSAP eases), durations, how things enter and leave, what never moves.
6. **Transitions** — how scenes hand over (the contract's rule: a transition belongs to the beat it leads into).
7. **Texture and effects** — grain, scanlines, shadows, which vendored items to use and how (§4.5); seek-safe only
   (the media-use skill's `references/media-treatments.md` rules apply to footage).
8. **Pacing** — typical scene length, how many scenes for 15/30/60 s.
9. **Captions and text cues** — how on-screen text maps to caption cues in this look.
10. **Sound** — mood for music, which actions get effects (only used when the run has sound).
11. **Do / Don't** — short lists.
12. **Building blocks** — the vendored items, components first, and the exact way to inline each into a beat.

Engine-specific notes belong to the render-engines plan; this plan only keeps `engines` in the schema.

### 4.5 Registry items: a pinned registry, vendored items, inlined into beats

- **Pin the registry for every run** (phase 1, a one-line change): `video/hyperframes.json` `registry` becomes
  `https://raw.githubusercontent.com/heygen-com/hyperframes/v0.8.222/registry`, the tag matching the pinned CLI. A
  test asserts the tag in `hyperframes.json` equals the version in `package.json` `netlifyAgent.hyperframes.version`,
  so they're bumped together. This helps every run, with or without a look.
- **Vendor what a look uses.** `npm run look:vendor <id>` reads `look.json` `registry`, runs
  `npx hyperframes@<pinned> add <name> --json` in a temp HyperFrames project, copies the written files into
  `looks/<id>/registry/<name>/`, and writes `registry.lock.json` (item, type, upstream path, tag, sha256 of each file,
  licence). Re-running it shows a diff; nothing changes without a commit. Vendoring gives offline runs, licences
  checked once in review, and an example that uses the same source the run gets.
- **Components first.** Each look lists components (`blur-in`, `grain-overlay`, `bottom-up-letters`,
  `browser-device-stage`, `agent-cursor`, `before-after-wipe`) before blocks; components merge into a scene by design.
- **Blocks are inlined.** `LOOK.md` "Building blocks" says how: copy the markup into the beat, scope its CSS to the
  beat (`[data-va-beat="…"] .x`), and rewrite its timeline calls inside the beat's `vaBeat` script, with
  `data-va-text` ids on editable text. Spike K1 writes these instructions for **every block the starter set uses**
  and proves the editor still edits them. A block that can't be inlined cleanly is replaced with a hand-written move.
- The agent may still search the registry itself (`catalog` works offline from the cached manifest) for things the
  look doesn't cover. The look's items are the preferred path, not a fence.

### 4.6 How a run gets the look

1. **Reconciler** (`src/domain/reconciler.ts`): when `version.look` is set, the manifest gets an optional
   `look: { id, key, sha256, hash }` (run manifest stays `v: 1`; `verifyRunManifest` adds a shape check: key inside
   the job prefix, both hashes hex, id matches the slug rule). Of the three `putManifest` calls:
   - render-unchanged (`:208`) gets no `look`: the run doesn't read it;
   - author-from-frozen, the fit run (`:232`), **gets `look`**: the fit prompt points at `context/look/`;
   - author/revision (`:317`) gets `look`, and its condition becomes `if (revision || media || version.look)`, so a
     manifest is written even when there's no revision or media.
2. **Pre-flight:** before starting an attempt whose version has a look, the reconciler checks the snapshot key exists
   (`blobs.list('sources', key)`, as for remix copies at `:258-260`) and fails the attempt with "This video's look
   snapshot is missing; restyle it to pick the look again" otherwise. No run starts, so no credits are spent.
3. **prepare-run** restores the look after library media, in the step order the render-engines plan owns (scaffold or
   restore and hydrate first, then library media, then look, then recording and scope files). It downloads the
   archive, checks its sha256, lists entries with a new helper beside `restoreArchive` (which is hard-wired to
   `video/`), refusing anything outside `look/` or with `..`, unpacks it to `context/look/`, then checks the
   `manifestHash` of the unpacked files against `hash`. It logs
   `look.restored { id, hash, files }`. On any failure it exits non-zero and the agent stops (the existing rule).
4. **Prompt** (the template number goes up by one, per the shared rule), only when there's a look:

   > The look for this video is in context/look/ (prepare-run puts it there). Read context/look/LOOK.md before you
   > design anything. context/look/example/ shows how its rules become a composition: skim the scene that matches the
   > one you're writing, and reuse its structure and building blocks, never its words or media. The look governs
   > layout, type scale, pacing, motion, transitions, textures and how colour roles are used. The brand in context/
   > still decides colours, logo, fonts and wording; where they disagree, the brand wins, and the request wins over
   > both. Write any colour role you derive as a literal colour. Copy any look asset you use (textures, effects)
   > into video/assets/look/, and add a credits line for any that needs one. Its name, as JSON:
   > `<<<{"id":"kinetic","name":"Kinetic type"}>>>`

   A restyle (the resolved snapshot's hash differs from the parent's, §4.3) adds:

   > This is a restyle into that look. Keep the story: the scenes in order, their beat ids, the on-screen words (and
   > their data-va-text ids), the media and any voice-over. Rebuild how it looks and moves to follow the look. A
   > scene's length may change by up to a quarter where the look's pacing needs it, never shorter than its voice-over
   > (run npx tsx scripts/voice.ts sync after any timing change); the total stays within the target.

   Keeping beat ids and text ids is what lets scoped revisions (redo a scene) and later text edits still line up.
   Comment pins are anchored by time and position, not beat ids (§1), so after a restyle existing pins stay on the
   version they were made on, as for any revision today; captions are regenerated by each render. Recorded narration
   never reaches this path (§4.3).
5. **Fit prompt:** `buildFitPrompt` gets the same look lines (not the restyle lines) when the version has a look.
6. **Music pick:** when Sound is on and nothing was picked, `music-pick.ts` puts the look's `sound.musicMood` words
   ahead of the request's mood words (`moodWords`, `src/domain/music-pick.ts:239`).
7. **Finalize** changes nothing: the composition is checked against the contract as today. Look assets the agent
   copied are in `video/assets/look/`, so they're archived with the source and survive revisions and remixes.

**Trust:** `LOOK.md` is instructions, like `context/`, so only people who control the repo or the deploy's env vars
add looks (built-ins by PR review; team looks, when they come, by an admin's zip, §12). Creators pick looks; they
can't upload one in v1.
The README's trust model gets one line saying so.

by PR", nobody has asked for private looks yet, and the zip is the largest validation surface in the plan, so draft 3

  role-dependent one); pickers hide disabled looks. A look's name and description are therefore visible to every
  signed-in role. (An `engineAvailable` flag for greying looks whose engines are off belongs to the render-engines

- `look?: string | null` on `POST /api/v1/videos`, `POST /api/v1/videos/{id}/revise`, `POST /api/v1/videos/{id}/remix`

- The version DTO gets `look: { id, name } | null`, additively (shared rule: the DTO grows, `editable` stays).
  Webhooks carry it because they embed the DTO (`src/domain/webhooks.ts:57`).

### 4.13 SDK and CLI

The SDK is **generated resource methods plus hand-written helpers** (cli-and-sdk plan draft 3). Each route carries an
`operationId` and an explicit `x-sdk` name (`{ resource, method }`), and the coverage test fails when a route has
neither a name nor `x-sdk: false`. So nothing in the SDK is hand-written for looks:

- `GET /api/v1/looks` carries `operationId: listLooks` and `x-sdk: { resource: 'looks', method: 'list' }`, which
  generates `looks.list()`.
- `look` is a body field on routes that already have their names, so `videos.create`, `videos.revise`,
  `videos.remix` and `plans.create` get it from the generated layer when the schemas change. No helper is needed;
  `restyle` is a CLI command, not an SDK helper.
- CLI (package `netlify-video-agent`, bin `video-agent`; after the cli-and-sdk plan's phase 3.1): `video-agent looks`, `--look <id>` on `create`, `revise` and `remix`,
  and `video-agent restyle <video> <look>` (sugar for `revise --look`). Errors map to exit codes by the CLI plan's
  rule (HTTP status, then code).
- **Local mode** (shipping, owner decision 2026-11-04: "make one locally, then deploy it for your team"):
  `video-agent local --look <id|path> "<prompt>"`. An id resolves against the looks bundled with the
  CLI at build time; a path points at a look folder, so contributors can try a look before their PR merges. Local
  mode runs from the CLI's bundled runtime, not from a checkout, and restores the look into `context/look/` through
  the file-based fetch mode the cli-and-sdk plan's phase 4 adds to prepare-run (it doesn't exist today: prepare-run
  fetches by key only).

### 4.14 The engine choice rule (owned here; the render-engines plan references it)

- A look lists its `engines`, preferred first.
- A new video's engine is `request.engine` when given, validated against the look's list (else
  `400 engine_not_supported_by_look`) and against the enabled engines (else `409 engine_disabled`); otherwise the
  look's first listed engine **that's enabled**; otherwise `hyperframes`.
- A look whose every engine is disabled can't be picked, and `PATCH /admin/settings` refuses it as the default. Showing
  it greyed ("needs Remotion (off)"), the `engineAvailable` flag on `GET /looks`, and the Advanced "Engine" select are
  the render-engines plan's UI (its phase 3), not this plan's.
- Revisions and remixes keep the version's engine unless the render-engines plan says otherwise; a restyle into a look
  that doesn't list the version's engine is `400 engine_not_supported_by_look`.
- Phase 2 ships HyperFrames-only looks, so until the render-engines plan's phase 2 the rule always resolves to
  `hyperframes`.

## 6. Admin controls

- **On/off per look** (`settings.disabled_looks text[]`, default empty). Turning one off hides it from pickers, MCP
  and plans, and refuses new picks with `409 look_disabled`. Versions that already use it keep it: retries,
  revisions that inherit it, and edits all still work.
- **Default look** (`settings.default_look text`, **default null**: no look). Applies to creates that omit `look`.
  Switching the default to `clean` is a decision for after spike K2 shows `clean` costs about the same as no look and
  looks at least as good (§14 Q3). The admin can set it at any time; when it's set, the setup page notes that API,
  MCP and Action callers get it too.
- No per-role restrictions in v1. "None" is always available (a setting to remove it is in §12).
- Migrations are sequenced with the other plans: engines phase 1 (`versions.engine`) lands before this plan's phase 2
  (`versions.look`, `settings.default_look`, `settings.disabled_looks`), and each PR regenerates OpenAPI.

## 7. Permissions, privacy and credits

- Listing looks: any signed-in role. Picking one: anyone who can create, revise or remix (unchanged roles).
- Restyle is a revision, so it's allowed wherever revising is (Creators can revise others' videos; the version is
  theirs, as today). On private videos the usual visibility rules apply first.
- Credits per run: a look adds `LOOK.md` (≤ 12 KB) and a skim of the example (≤ 24 KB) to what the agent reads; spike
  K2 measures it. The expectation is under 5 % of a run. A restyle is a full authoring run, priced like a revision.
- **Credits for building this.** Several gates are **live tests** (a script that makes real videos on the production
  site and checks them; costs credits). Owner decision (2026-11-04): each live test runs `--dry` first, which prints
  the steps and the projected credits and spends nothing; then the owner is asked before that gate runs, with a credit
  ceiling. There's no blanket pre-approval, and a re-run is asked again. K2 is not on production but spends credits
  the same way, so it follows the same rule:

  | Gate | Runs | Ceiling (credits) |
  | --- | --- | --- |
  | K2 (does a look change the output? branch-deploy runs, no server code) | 6 | 900 |
  | Gate 2 (one per look, one restyle, one retry after a look change) | 5 | 700 |
  | Gate 3 (the owner makes one video per look in the app) | 3 | 500 |
  | Gate 4 (five new looks, one sample each) | 5 | 800 |
  | **Total** | about 19 | **about 2,900** |

  Local mode (once the cli-and-sdk plan's phase 4 lands) moves contributors' tries off credits entirely.
- Looks hold no personal data. Snapshots live under the video's prefix and are deleted with it.

## 8. Contributing a look

The flow `looks/README.md` and the CONTRIBUTING guide describe:

1. `npm run look:new <id>` copies `looks/_template/` and fills `id`, `name` and `since`.
2. Write `LOOK.md` (the required sections), build `example/` (a 10–15 s, 3–5 scene composition about the fictional
   product "Orbit"), and list registry items in `look.json`, components first.
3. `npm run look:vendor <id>` vendors the registry items and writes the lock file.
4. `npm run look:check <id>` (§9) until it passes.
5. Render the preview by hand with the documented commands in `looks/README.md`: `npx hyperframes@<pinned> render` on
   the example, then one `ffmpeg` line that cuts it to ≤ 6 s at 540 px and writes `preview.mp4` and `poster.webp`
   within the size caps. (A `look:preview` command and staleness tracking are in §12.)
6. Try it on real prompts: `video-agent local --look ./looks/<id> "<prompt>"` (cli-and-sdk plan) with your own agent,
   or a deployment of your own. Render the three prompts in `looks/PROMPTS.md` (a 16:9 launch, a 9:16 social clip, a
   30 s explainer with a chart) and attach the GIFs to the PR.
7. Open the PR. CI runs `look:check` on the `pull_request` trigger only (never `pull_request_target`), so a
   contributed example runs in CI's Chrome with no secrets. Review checks the quality bar: original (no imitation of
   a specific company's, film's or show's identity), readable at phone size, works with an orange, a blue and a
   near-black brand accent, all four shapes, seek-safe motion, licences in order.

## 9. `look:check`

`npm run look:check [--static] [id…]` (all looks when no id). One line per problem, `look:<id>: <problem>`.

**The static half** (`--static`; runs in the Netlify build and in CI; no browser):

- `look.json` matches the schema; `id` matches the folder; `registry` matches `registry.lock.json`.
- `LOOK.md` exists, is ≤ 12 KB and has every required section; `example/index.html` is ≤ 24 KB.
- File rules and size limits (§4.1); `credits.json` lists every file in `assets/` with an allowed licence (CC0,
  CC BY, OFL, Apache-2.0, MIT, or "own work").
- Vendored items' sha256 match the lock file, and the lock's tag matches the pinned HyperFrames version.
- `example/` passes `validate()` from `src/lib/contract.ts` (the same check as `scripts/check-contract.ts`); it has
  no URLs outside the folder and no `Date.now()` or `Math.random()` (the HyperFrames rules in `video/AGENTS.md`).
- The example uses only colour roles listed in `look.json` `colors`, writes every derived role as a literal colour,
  and every text element has a `data-va-text`.
- Every binary file sniffs as what its extension says (PNG, WebP, JPEG, WAV, MP3, Ogg magic bytes; WOFF2 too once
  fonts return), so only real images and audio reach Chrome at render time.
- `preview.mp4` and `poster.webp` exist, sniff as what they claim, and are within size.

**The browser half** (default without `--static`; CI only, after Playwright's Chromium is installed,
`.github/workflows/ci.yml:24`): copies `example/` into a temp HyperFrames project with `video/`'s vendor files and
config, and runs `npx hyperframes@<pinned> check` (lint, runtime, layout, motion, contrast) until it reports 0 errors.

CI adds `npm run look:check` after the Playwright install step. (`--json` output is in §12.)

## 11. Tests

**Unit (vitest)**

- Schema: every field's bounds, including `recording` and `recording: false`; id/folder mismatch; unknown keys
  refused.
- Hash and archive: the same files in a different order give the same hash; one byte changed gives a different one;
  the archive is byte-identical across two builds.
- Resolution: explicit `null` never becomes the default (create, revise, remix, plans); create with `look` omitted
  uses the plan, then the default; revise and remix with `look` omitted keep `null` when the parent has none, even
  with an admin default set; the parent's own id at the same hash isn't a restyle; the narration and scope refusals.
- Engine choice: request engine validated against the look; first enabled engine; all-disabled refused as default.
- Prompt: with no look, byte-identical to today's for the same input: the golden fixture
  `test/fixtures/prompt-silent.txt` (`src/domain/prompt.test.ts:76-79`) is not regenerated; with a look, the look lines appear once, the name is fenced and sanitised; a restyle adds the restyle lines; the fit prompt
  gets look lines but not restyle lines; a render-unchanged prompt never mentions a look.
- `look:check` on fixtures: a good look passes; each rule has a failing fixture (missing section, oversized
  `LOOK.md` or example, bad licence, a `color-mix` derived role, example breaking the contract, external URL,
  `Math.random`, lock tag mismatch, an `assets/` over 1 MB, a `.png` that isn't one).
- `hyperframes.json` registry tag equals `netlifyAgent.hyperframes.version`.
- `writeTarGz` with `prefix: 'look/'` names entries under `look/`; without it, output is byte-identical to today's
  (remix copies unchanged).
- Music pick: the look's mood words come first.

**Integration (in-memory store and PGlite)**

- Create with `look`, without it (default applied; none by default), with `null`, with an unknown id (400), a
  disabled id (409).
- Snapshot copy: reservation row committed before the copy; read-back mismatch fails the request; an idempotent replay
  leaves the copy unadopted and the sweep deletes it; a successful create marks the reservation done.
- A second revision picking a look whose first attempt failed: the reservation row is re-opened, not duplicated (no
  unique-index error); a version never references a key that no committed version adopted; an unadopted blob that
  exists is copied again, not trusted.
- Pre-flight: a version whose snapshot key is gone fails its attempt before any run starts, with the restyle message.
- The fit run's manifest (author-from-frozen) carries `look`; the render-unchanged manifest doesn't.
- Revise inherits the parent's snapshot (same key and hash, no new blob); revise with `look` restyles (new snapshot);
  restyle of a narrated version is 409; render-unchanged copies `look` for display; `look` on render-unchanged,
  fit-to-narration or with `scope` is 400.
- Remix keeps the source's look under its own prefix; remix with another look.
- Retry after the catalog changed: the attempt's manifest still points at the original snapshot.
- Plans: a chosen look reaches the brief as `chosen_look`; with none chosen, the router's template picks the first
  matching enabled look; the frozen plan's look is used by create.
- Admin settings round-trip; a disabled look is refused as default and for new picks.
- MCP: `list_looks`; `create_video` with `look`; `mcp-catalog` test.
- Webhook payloads carry `look`.
- Delete a video: its `looks/` snapshot is in the cleanup prefix.
- `prepare-run` (with the fake fetch used by today's tests): restores to `context/look/` after media; refuses a hash
  mismatch, an entry outside `look/`, and a `..` path.

**Playwright (`npm run test:ui`)**

- Picker opens from New video with posters only (no preview requests until hover or focus), plays a preview on hover
  and focus, shows posters only with reduced motion, picks with the keyboard, and the create
  request carries `look`.
- Restyle dialog shows the cost line and sends a revision with `look`; it's hidden for narrated versions.
- Admin turns a look off; a Creator no longer sees it in the picker.
- `/docs/looks` renders every catalog look.

**Live test: `scripts/e2e/looks.ts`** (pattern: `scripts/e2e/remix.ts`; run `--dry` first, then ask the owner)

- `--dry` prints the steps, the looks to test and the projected credits, and makes no requests.

## 12. Not in v1 (designs kept)

- **Team looks (`LOOKS_ZIP_URL`).** Moved out of v1 in draft 3 (§4.7, §14 Q7). Design:
  - An optional env var (scopes: builds and functions), the same idea as `BRAND_ZIP_URL`: a zip of look folders at
    its root.
  - The build fetches it **streaming, aborting at 25 MB and after 20 s**, and any failure falls back to built-ins only
    without breaking the deploy (the URL is never logged). Caps: at most 2,000 entries and 20 looks. It refuses
    entries with `..`, absolute paths or symlinks, unpacks into `looks-team/` (gitignored), and runs the same schema
    and static checks (§9), including content sniffing of every binary.
  - **Ids must be unique**: a team look with a built-in's id is dropped with a logged reason
    (`looks.team_collision`) and listed on `/setup`.
  - Valid team looks join the catalog with `source: 'team'` and get archives in `looks-build/` like built-ins, so the
    snapshot path is the same; no run-time download (netlify-agent-kit `files` isn't used for looks).
  - Their strings are capped by the schema, rendered as text, and enter prompts only through `sanitizeBrief` or the
    planner's data blocks. Names and descriptions are visible to every signed-in role, so they're no place for
    anything private.
  - The Admin Looks section shows each look's source and lists dropped team looks with the reason.
  - A test covers a zip over the caps, with a `..` entry, and with a colliding id.
  - (`BRAND_ZIP_URL`'s build fetch has no size cap or timeout today, `scripts/build.ts:35-51`; the same streaming cap
    would suit it, as separate work.)
- **Fonts shipped inside looks** (phase 4.3). Design: `look.json` `fonts: [{ role, file, license, useWhen }]`
  (`role` such as `mono` or `hand`; `license` OFL-1.1 or Apache-2.0; `useWhen` in words, ≤ 80 chars), WOFF2 files in
  `assets/fonts/` counted in the 1 MB `assets/` cap and sniffed (`wOF2` magic), used only when the brand has no font
  for that role (§3).
- **Tag filter chips and `pace`.** Design: chips from `tags` above the picker grid (multi-select, AND), and
  `pace: "calm" | "medium" | "fast"` in `look.json` shown on the card and passed to the brief as part of `chosen_look`.
  Worth it past about a dozen looks.
- **`sound.sfx`** in `look.json`: a one-line hint for which actions get effects, passed to the run's sound lines.
  v1 keeps this in `LOOK.md`'s Sound section, which the agent reads anyway.
- **Engine greying and the "Engine" select** in the picker: the render-engines plan's UI phase (§4.14).
- **A README GIF per look.** v1 shows one poster strip linking to `/docs/looks`.
- **The model choosing a look in plans.** Design: the brief step gets the enabled catalog as data (id, name,
  description, bestFor; at most 20 looks, about 1.5 KB) and returns `look: "<id>" | null`, the way it decides
  sound. v1 uses the deterministic template match (§4.11) instead: no extra model output to validate, and the same
  plan always gets the same look.
- **Removing "None"** (`settings.looks_allow_none boolean`): hides the None card and refuses `look: null` for
  non-admins. Only worth it for a deployment that wants every video in a look.
- **Team looks overriding built-ins by id.** Design: a team look with a built-in's id replaces it for this deployment,
  logged (`looks.team_override`) and shown on `/setup`. v1 requires unique ids and drops collisions.
- **`look:preview` and staleness tracking.** Design: `npm run look:preview <id>` renders the example with the pinned
  HyperFrames, cuts the clip and poster, and writes `preview.json` (example hash, HyperFrames version); `look:check`
  then fails when the example's hash no longer matches. v1 documents the two commands and reviewers look at the clip.
- **`look:check --json`** for machine-readable CI output.
- **"Updated since" and "Use the new version?"** Design: the version DTO adds `look.updated` (the catalog has a newer
  hash for that id), the video page says "Kinetic type has been updated since this video was made" with a button that
  restyles into the current version. v1: restyling into the same look does the same thing.
- **The look on the Library tile's meta line** (when it isn't the default), and a Library filter by look.
- **Animated WebP previews** (≤ 500 KB) instead of MP4, if MP4 hover clips prove heavy on mobile.
- **Look from a reference** (a video, a URL or a few screenshots → a drafted `LOOK.md`). Promising, but a drafted
  look still needs a human to review it, and the picker needs a good set of real looks first.
- **Looks made in the app** (an admin editor that writes `LOOK.md` and uploads assets to Blobs). Team zips (above)
  would cover private looks before then.
- **Per-deployment previews in your brand.** The picker shows previews in the neutral example brand. "Preview with my
  brand" would be a short real run (credits) per look; later, maybe as an admin action that renders all of them once.
- **Restyle of videos with recorded narration**, keeping every scene's length exactly (the agent rebuilds visuals
  within fixed beat lengths, and `checkNarrationModified` stays green).
- **Mixing looks per scene.** One look per video.
- **Usage by look** on the Admin Usage page.
- **A look benchmark** (three fixed prompts rendered and scored per look). It belongs with a benchmark harness, which
  isn't planned yet.
- **Creator-uploaded looks.** A look is instructions to the agent; v1 keeps that to repo owners and admins.
- **Engine-specific look notes** (`LOOK.<engine>.md`, `example-<engine>/`): the render-engines plan designs these.

## 13. Risks

| Risk | Likelihood | Mitigation |
| --- | --- | --- |
| Looks don't differ enough because the agent leans on its habits | Medium | Concrete rules, a full example, vendored moves; K2 on a spike branch checks with the owner before phase 2 |
| The agent copies the example's words or media | Medium | Fictional product, placeholder words, explicit prompt rule; K2 measures it |
| Inlining registry blocks is too fiddly for the agent | Medium | K1 writes exact instructions for every block used; looks list components first; hand-written moves where needed |
| A default look silently raises cost for API, MCP and Action callers | Medium if defaulted | Default stays none until K2; the setup page notes it when an admin sets one |
| Restyle is one click for a full run, often on others' videos | Medium | Cost line in the dialog, no bulk restyle, the usual role rules |
| Brand and look fight (unreadable contrast, off-brand colour) | Low–medium | Colour rule (§3), `hyperframes check` contrast in CI, review with three accents |
| Look strings reach prompts and pickers | Low | Schema length caps, `sanitizeBrief` and data blocks, text-only rendering |
| A snapshot goes missing and retries burn credits | Low | Deterministic reservation, adopt-only-committed rule, pre-flight before each attempt (§4.3, §4.6) |
| Restyle via MCP spends a full run without the web dialog's cost line | Low–medium | Tool descriptions say a different look is a full run; the skill asks before restyling others' videos |
| A look's assets bloat every later archive of a video | Low | `assets/` ≤ 1 MB per look; only what the agent copies lands in `video/` |
| Contributed example JS in CI | Low | `pull_request` trigger only, no secrets |
| Picker bandwidth on mobile | Low | Posters only until hover or focus; 500 KB clip cap |
| Repo size from previews (8 × ≤ 560 KB) | Low | Size caps; previews are the only binaries most looks have |
| Function bundle grows | Low | One archive per look, ≤ 3 MB each; K3 measures |
| Name collision with `RENDER_QUALITY=looks` confuses people | Low | Naming rules, docs wording, §14 Q1 |
| Community looks imitate a real brand's identity | Low | Contribution rules and review |
